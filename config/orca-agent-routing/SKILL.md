# Orca agent routing

If you have Task/Dispatch IDs or a worker assignment, follow that assignment.
Do not become a lead or spawn nested workers unless explicitly assigned to do so.

In an Orca lead chat, handle only trivial administrative actions directly. Delegate
codebase searches, locating definitions/callers, source gathering, research, and
small well-defined edits to Haiku or Luna. For substantial work, use
the routing below without asking the user to open a desktop shortcut. Keep the
lead's selected model, effort, speed, and permissions. These saved worker choices
are user-authorized model selections; the user need not repeat a model in every
task. They take precedence over the generic guide's model-omission and native
subagent preferences. They do not expand the task or the session's permissions.

Confirm Orca context from the session's Orca runtime identity/environment or the
user's explicit request. An installed Orca executable or a mobile-related task
alone is insufficient. Use Paseo's own profiles and tools in a Paseo-led chat.

## Choose the worker

Read the saved profiles and every profile's notes in
`~/.agents/skills/orca-agent-routing/profiles.json` before selecting a worker.
That file is generated by
`config/scripts/desktop-distribution/macos/configure-native-orchestration.mjs`
in the local Orca source checkout, using Orca's live shortcuts and matching Paseo
profiles. Grok is an explicit override from Orca's native preset. The file records
the exact commands and settings;
do not infer model IDs from the role names below. A newer live shortcut wins over
the snapshot only after confirming it is the user's saved choice and refreshing
the generated snapshot. Reconcile disagreements with Paseo before launching,
except for the explicit native-Grok override in Orca.
In Orca, this skill's launch and review instructions supersede helper-specific
Paseo notes. After an Orca update, rerun the installer if the loader link or any
provider's skill discovery is missing; the standalone routing skill is separate
from Orca's bundled lifecycle guide.

Apply these choices in order; an explicit user choice always wins:

| Work                                                                                                            | Profile key | Session use                                  |
| --------------------------------------------------------------------------------------------------------------- | ----------- | -------------------------------------------- |
| UI implementation, layout, styling, interactions, accessibility, polish                                         | `claude`    | Separate implementation and review sessions  |
| Independent plan review before substantial changes; code review afterward                                       | `claude`    | Independent of the implementer               |
| Screenshot/asset inspection, drawings, visual QA, bounded app work, source-grounded writing, small visual fixes | `terra`     | Reuse a suitable idle worker                 |
| Short, self-contained research, source gathering, small fix, narrow implementation                              | `haiku`     | Fresh conversation for each new task         |
| Continuing related bounded research or implementation that benefits from retained context                       | `luna`      | Prefer the matching successful idle worker   |
| Other general coding, complex debugging, multi-file refactors, integration and meaningful tests                 | `sol`       | Default implementation worker                |
| Requested Grok work or a useful additional implementation/bug-hunting perspective                               | `grok`      | Supplemental; use Orca's native `grok` agent |

Use Claude Opus 5.5 (`claude-opus-5-5`) at Medium effort (`medium`) for
the `claude` role, including UI implementation and independent plan/code reviews.
Keep Medium unless the user explicitly requests a different effort.

Use Haiku for a short task with one question or narrow edit, a concrete deliverable,
and a clear stopping condition. Use Luna when several related searches, research
steps, or small edits will benefit from retained project context. Long means a
continuing bounded assignment, not an open-ended project. Escalate complex debugging
or broad implementation to Sol. Routine code searches are Haiku/Luna work.
For ongoing bounded work, prefer Luna over starting another short-task Haiku.
The lead owns image concepts, visual direction, image briefs, and design critique;
Claude implements the UI. Terra may critique the rendered result. Assign app or
image actions only after checking that worker's own tools. Workers do not inherit
the lead's connected tools. Escalate complex work to Sol or the lead.
For a user-named model without a saved profile, use the appropriate role's saved
permission mode and other compatible settings, overriding only what the user
specified. Report incompatible settings rather than expanding permissions.

## Launch through Orca

Use the `orchestration` skill to resolve the session's Orca executable and read
its version-matched guide once. Keep all delegated work in Orca's supervised Run.
Do not use the standalone `codex-orchestrate` helper, Paseo agents, or provider-native
subagents for an Orca assignment. Report the chosen role/model in a brief update.

Preserve the complete saved launch bundle: provider, model, effort, Fast/service
tier, and permission mode. Use native **chat** workers for all six saved profiles,
including Haiku and Grok. Do not pre-create a terminal or use the short
`worker-start --agent` route for these profiles: that route can follow a saved
CLI preference and stop at a workspace-trust menu. The native `agent.launch`
API accepts their complete per-chat settings.

Confirm this lead's own Orca session identity before preparing workers. Resolve
the intended workspace with the selected CLI; use its exact `id:`, `identity:`,
`folder:`, or `path:` selector, not the runtime server's implicit current folder.

1. Run the installed native-chat adapter:
   `node ~/.agents/skills/orca-agent-routing/scripts/prepare-chat.mjs --profile haiku --worktree '<exact-selector>'`.
   Replace `haiku` with any of the six saved profile keys, including `grok`. For independent Claude
   reviews, use `--profile claude --review`.
2. The adapter calls Orca's native `agent.launch` with `surface: chat`, creates
   an unprompted background chat, and verifies its model, effort, speed, and
   permission settings. Only continue when `readyForDispatch` is true and
   `launch.outcome.kind` is `structured`.
3. Register `launch.outcome.handle` with `orchestration worker-start --terminal`,
   the same exact `--worktree`, a self-contained `--spec-file`. Add `--keep-open` only when the worker
   will be reused for related work or the user asked to retain it.
   Here `--terminal` accepts the native chat's address; it does not turn the
   chat into a terminal. Do not add `--agent`, `--model`, or `--effort`.
4. Inspect the receipt and follow its `next`. End the turn after starting the
   independent workers. Orca wakes the lead with their results; do not poll.

On an uncertain chat preparation, retain the printed `operationId`, inspect the
returned resource, and retry only the identical preparation with
`--operation-id <same-id>`. Do not create another fresh chat blindly. A prepared
chat is not a supervised worker until `worker-start` accepts it.

Grok uses this same preparation and registration flow. Its saved `launchOptions`
are preserved, including its normal Orca permission setting; the adapter does
not introduce a permission bypass. Use Orca's native Grok account, never Pi,
`grok-cli/grok-build`, or `pi-grok-cli` as a passthrough.

Before dispatching any profile, require the structured-chat receipt and matching
settings from the adapter. Never submit task text to a shell, trust menu, login
screen, or fallback terminal. If preparation fails, inspect that operation and
report the actual blocker; do not retry through a terminal. Workspace trust and
provider sign-in are separate: changing trust cannot repair an expired login.

If native chat support/settings are refused for a saved profile, leave the task
undispatched and report the blocker. Do not fall back to its CLI shortcut.
For a different, user-named agent that has no chat support, read the guide's
`references/low-level-topology.md` before a custom-argv launch. Use the exact task
workspace and grant only explicitly needed extra directories with a supported
directory-grant option (Claude's `--add-dir`). Do not suppress a trust prompt
with blanket permission bypasses. A terminal waiting at workspace trust has not
accepted its Task.

Review assignments are read-only. The native adapter's `--review` uses Claude's
`interactionMode: plan` while retaining its saved model, effort, and Auto base
permission. Terminal-only review fallbacks replace `--permission-mode auto`
with `--permission-mode plan`. Tell the reviewer to return findings and complete its Orca Task,
without writing a plan file or asking for plan approval. Give it the diff/patch,
base, changed files, and check
results. The lead runs validation. Do not claim that Auto or a prompt alone
enforces read-only access. Skip routine review rounds for trivial changes.

Only use this chat's runtime identity. If Orca reports `no_active_sender_terminal`,
do not borrow another pane's handle or create untracked workers. Report the launch
gap and continue authorized work directly when possible. For a failed/uncertain
start, follow the recovery reference before any retry. A created terminal alone
does not prove that a supervised worker started.

Grok workers use the native `grok` agent and its existing Orca login. A Grok
failure must not trigger a Pi passthrough or credential changes. If any selected provider/model/setting is unavailable,
report that accurately and continue with a suitable available route within the
user's instructions. Do not switch to paid API access or claim a model was used
without a successful launch receipt.

## Coordinate and verify

Reuse only successful idle workers owned by this Run with matching model,
effort, permissions, project, and useful context. Haiku starts fresh for each new task unless the
user explicitly asks to resume. Keep a successful Luna worker for related bounded
follow-ups and re-read files changed since its last assignment. Keep Sol, Terra,
Claude, or Grok only while their context is useful to the current work. Independent
reviewers must remain separate from implementers. After accepting a one-off result,
or when related work is finished, use the guide's worker-release flow for the exact
owned resource. Inspect the release receipt: an adopted/pre-existing chat may be
retained for safety. Never force-close an unowned/user-kept chat, kill a PID, or
assume that omitting --keep-open closes an adopted native chat. Preserve reviewable
results and respect explicit user retention. Failed, mismatched, or misleading
sessions get a fresh replacement rather than automatic reuse. Give each follow-up new scope, file ownership,
constraints, and acceptance checks; never assign concurrent tasks to one worker.
Preserve unrelated edits. Use the current workspace for read-only or disjoint
assignments; let Orca create a worktree when edits conflict. Use `orchestration send`
for follow-ups and the guide's reply/completion flow. Review worker evidence,
integrate, and verify the outcome before reporting completion. Distinguish saved
configuration, actual worker launch, rendered UI, and on-phone verification.
